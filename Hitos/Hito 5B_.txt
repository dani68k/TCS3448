==================================================
PRINCIPIO FUNDAMENTAL
==================================================

Separar claramente:

ACQUISITION
y
RECORDING

No son lo mismo.

Acquisition:
START / STOP actual del sensor.

Recording:
START RECORDING / STOP RECORDING.

Estados válidos:

Acquisition RUNNING
Recording OFF

→ sensor funcionando y mostrando histograma
→ no se guarda nada

Acquisition RUNNING
Recording ON

→ sensor funcionando
→ cada TCS3448Sample se guarda

Acquisition STOPPED
Recording OFF

→ estado normal detenido

No permitir:

Acquisition STOPPED
Recording ON

Si se intenta iniciar Recording sin adquisición activa:
devolver error.

Ejemplo:

ACQUISITION_NOT_RUNNING

==================================================
13. START RECORDING
==================================================

Flujo:

1. usuario pulsa START RECORDING
2. web envía comando
3. ESP32 valida:
   - filesystem disponible
   - acquisition RUNNING
   - no hay recording activo
   - session name válido
   - existe espacio suficiente
4. crea nombre único
5. abre CSV
6. escribe metadata
7. escribe header
8. entra en estado RECORDING
9. devuelve ACK
10. web actualiza estado

No mostrar Recording ON antes del ACK.

==================================================
14. WRITE SAMPLE

DataLogger.writeSample(sample)

Evitar:
- String gigantes
- malloc/free repetidos
- streams dinámicos pesados

Preferir:
- buffer estático/local limitado
- snprintf
- escritura secuencial

==================================================
19. DESCONEXIÓN BLE DURANTE RECORDING
==================================================

Decisión importante:

NO detener Recording automáticamente por una desconexión BLE.

El ESP32 debe continuar registrando de forma autónoma.

Motivo:
la función DataLogger debe poder operar independientemente del navegador.

Si el navegador reconecta:

GET_STATUS

debe devolver:

Acquisition: RUNNING
Recording: RUNNING
Current file: ...
Samples: ...

La web debe recuperar el estado real.

IMPORTANTE:
No aplicar a Recording la misma lógica del LED AUTO que actualmente pueda detener adquisición al desconectar sin revisar arquitectura.

Analizar cuidadosamente comportamiento actual de disconnect.

Si actualmente la desconexión BLE detiene Measurement:
documentarlo y decidir cómo reconciliarlo con el requisito de recording autónomo.

Prioridad:
NO introducir un comportamiento inconsistente.

Si la arquitectura actual hace imposible mantener adquisición sin BLE,
explicarlo antes de modificar la lógica.
